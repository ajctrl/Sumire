# フォーク元への自動追随

`KazumaProject/JapaneseKeyboard` の正式リリースを毎日 03:23 UTC に確認し、
更新PRを作成します。ビルド・テストに成功した更新だけを `dev` に自動マージし、
署名付きAPKをGitHub Releasesに自動公開します。
Actions の **Sync upstream release → Run workflow** でも実行できます。
スケジュールは既定ブランチ `dev` で有効になり、実行時刻はGitHubの混雑で遅れる場合があります。
準備が成功すると、別の **Validate and publish upstream update** が自動で検証・マージ・公開を行います。

## 取り込み方法

- `.github/upstream.json` に取り込んだタグとコミットを記録します。初期値は `v1.7.128` です。
- 正式リリースの最新版だけを対象とし、プレリリースや開発ブランチには追随しません。
- 通常のGitマージで、`com.example.sumire` のアプリID、署名設定、Sumire Sync連携を保持します。
- PRブランチは `upstream/<タグ>-<devのSHA先頭12文字>`。同じ更新の再実行でforce pushは行いません。
- **Merge commit** で上流の履歴を保持します。更新PRを手動マージする場合もSquash/Rebaseは使わないでください。
- 検証済みの `dev` コミットから、上流と同名のタグ（例: `v1.7.128`）とGitHub Releaseを作成します。
- 更新がない日も未公開リリースを確認し、公開に失敗していれば再試行します。
- 手動のフォーク版（例: `1.7.128.2`）は定期実行では公開しません。
- 手動版の後に新しい上流が出た場合、`app/build.gradle` のバージョン名は新しい上流に合わせ、
  `versionCode` は上流値と現在のフォーク値+1の大きい方にします。バージョン番号だけの競合は処理しますが、
  その他のテキスト競合はsol-highで解決し、大きな変更・破壊的な変更は人の確認待ちにします。
  APIキーがない場合は従来どおり停止して手動確認を求めます。

## APIによる競合解決

`OPENAI_API_KEY` をリポジトリの **Settings → Secrets and variables → Actions → Secrets**
に登録すると、定期・手動どちらの実行でもCodex CLIを起動します。
定期実行で上流の更新確認、競合修復、変更全体のリスク確認、ビルド・テスト、自動マージまで進めます。
モデルが人の判断を必要とした場合や、検証に失敗した場合は停止します。
APIキー未設定では、競合修復も変更全体のリスク確認も通過できません。
手動で修復・再開する場合は **Sync upstream release → Run workflow → dev** で起動します。
既定は **sol-high**（モデル `gpt-6.1-sol`、`reasoning.effort: high`）です。
モデルを変更する場合はActions Variable `OPENAI_MODEL` を設定します。推論設定はhighを使います。
公式Codex CLI `0.169.0` をActionsでインストールし、`codex exec` を使います。
Codexが必要なファイルを読み、隔離した作業コピーを直接編集します。JSONは完了・確認待ち・理由の報告だけに使います。
外側の処理は作業コピーの実際の差分を検査し、対象のチェックアウトへ反映します。
修復するCodexは別OSユーザーのworkspace-writeサンドボックスで、`.git`・`.codex`・`.agents` を除いた作業コピーを参照します。
作業コピーと結果ファイルの所有者は親プロセスに保ち、Codexのグループには作業コピーの編集・結果出力の権限を与えます。
編集後は親へ所有権を戻して差分を回収し、モデルによる変更全体の確認は読み取り専用で行います。
Codex専用ホームは別ユーザー所有とし、成功・失敗・予算中断のいずれでも削除します。
APIキー・GitHubトークン・Artifactの実行資格情報はCodexへ渡しません。
ビルド・テストは後段の検証ジョブで行い、Codex内では実行しません。

### 通常の変更は任せ、大きな変更・破壊的な変更は人が確認

アプリのコード、テスト、Gradle・依存関係、Manifest、リソース、文書など、通常のテキスト競合を
モデルに任せます。文言だけに限定する許可リストや、3箇所・20行・4KBという制限は撤廃しました。
両側で追加されたテキストファイルや、実行属性のあるテキストファイルも対象です。

モデルは、競合を解く際に人の判断が必要かを判定します。さらに、競合のなかった変更も含めた
**解消後の差分全体を、コミット・push前にもう一度評価**します。たとえば次の場合は確認待ちにします。

- 大規模な設計・挙動変更や、後方互換性を壊すインターフェース変更。
- データ消失、危険な移行、認証・権限・署名の弱体化、Sumire Sync機能の欠落。
- テストを通すためだけの検証削除・無効化、意図が曖昧な解消、判断に必要な情報の不足。

ファイル名や行数だけで危険と決めず、変更内容をモデルが判断します。
仕様変更に根拠のあるテスト更新は許可しますが、失敗を隠すためにテストを弱めることは認めません。
確認待ちの理由はActionsログとサマリーに出し、その更新をマージしません。
同じ変更への確認待ち判定も保存し、毎日の実行で同じ問い合わせを繰り返しません。
人が修正して `dev` や上流コミットが変われば、新しい変更として評価します。

自動化自身（`.github`）の変更、上流履歴の分岐、バイナリ・シンボリックリンク・削除を伴う
構造的な競合など、現在の修復処理で扱えないものはモデルに任せず停止します。
[conflict-policy.py](../.github/scripts/conflict-policy.py) はパス・競合形式を確認し、
通常のコードを内容のキーワードで一律に排除しません。

モデルの判断は安全性の保証ではないため、フォークの連携保持チェックとビルド・テスト・Lintも必須です。

### 解決と検証

- Codexには競合ファイルの一覧を渡し、必要なファイルを自分で調べて直接編集させます。
  競合箇所に加え、解消に必要な関連ファイルの変更・追加・削除も扱います。ソース中の命令文はデータとして扱います。
  自動化の変更、シンボリックリンクやバイナリの変更、不正パス、未解消マーカーがあれば適用せず停止します。
- Codexの各モデル要求はローカルの予算ゲートウェイを経由します。
  ツールの結果を含む入力を毎回計数し、生成前に予約・応答後に精算します。
  予算到達や通信失敗後はゲートウェイを停止し、CLIが再試行しても追加の生成を許可しません。
  編集途中のファイル差分と調査の会話履歴を保存し、予算中断後は次回の作業コピーへ復元します。
  完了した修正も保存し、同じ更新の再開時にはAPIで作り直しません。
- 生成回数の一律上限は設けません。出力枠は最初から、モデルの最大出力・コンテキストの空き・
  当日の残り予算（今回の入力と余裕256トークンを除く）の最小値を使います。推論もこの出力枠に含みます。
  固定8Kからの開始や、出力枠を倍増しての自動再生成は行いません。
  当日枠が尽きた場合は一時中断し、モデル・コンテキストの上限で回答が切れた場合は確認待ちにします。
  拒否・不正な置換・その他の不完全な応答・通信エラーも自動再試行せず停止します。
- 編集済みの差分と、当日の確定使用量・応答不明の予約分をArtifactへ保存します。
  再開時は同じSumire・上流コミット、同じポリシー、同じ競合内容の修正だけを再検証して再利用します。
- 作成済みブランチは、親・同期記録・自動化コード・ツリーIDとポリシー版を確認して再利用します。
  制限前の実装で作った修正を、そのまま再利用することは認めません。
- 解決後もビルド・テスト・Lintが通るまでマージしません。
  テスト失敗後にモデルへテストを弱めさせたり、修正を繰り返させたりしません。
- 確認必須の場合、Actionsログに対象と理由を出し、マージを中止します。
  現時点では確認待ちPRを自動生成せず、Actionsの失敗通知で人に知らせます。

### 当日の累計200Kで一時中断し、次回実行で再開

競合修復と変更全体のリスク判定は同じ日次予算を使います。
既定では、入力・出力・推論を含むUTC日ごとの累計を **200,000トークン**
で区切ります。Actions Variable `OPENAI_DAILY_TOKEN_BUDGET` で変更できます。
次の呼び出しの入力数を事前計数し、日次予算の残りから入力数と余裕256トークンを除いた分まで
出力を許可します。モデル・コンテキストの上限も超えない値を予約してから生成を開始し、
応答後はAPIの `usage.total_tokens` で実消費へ精算します。大きい出力枠を指定しても、未使用分は消費に計上しません。
入力の計数に失敗した場合や、入力自体がモデル・日次上限に収まらない場合は確認待ちにします。

既定の `gpt-6.1-sol` と、`gpt-6-astra` / `gpt-6-sol` / `gpt-6-luna` のモデル仕様は、
コンテキスト1,050,000・最大出力128,000トークンとして実装しています。
[モデルの公式仕様](https://developers.openai.com/api/docs/models/gpt-6.1-sol)に基づく値です。
ほかのモデルを使う場合や仕様が変更された場合は、Actions Variablesの
`OPENAI_MODEL_CONTEXT_WINDOW` と `OPENAI_MODEL_MAX_OUTPUT_TOKENS` に公式の上限値を設定してください。
これは小さな出力枠を独自に設ける設定ではなく、利用モデルの仕様を指定するための設定です。
古い途中保存に含まれる8K・倍増の出力枠は無視し、再開時点のモデル仕様と残り予算から再計算します。

生成前の予約、応答後の使用量、修正完了のたびにGitHub Artifactへ保存します。
通信切断・強制終了で実際の課金量が分からない要求は、予約した最大量を当日の使用枠に残します。
Artifactの直近2世代を交互に更新し、古い側だけを削除して保存するため、アップロードの途中で
中断しても直前の保存分が残ります。保存できない場合は、追加のAPI呼び出しを始めず停止します。

予算不足は修復失敗ではなく **一時中断** です。Actionsはnoticeとサマリーを出して正常終了し、
その実行では検証・マージ・リリースへ進みません。同じ日に再開しても使用量は引き継ぎます。
翌日03:23 UTCの定期実行で日次使用枠をリセットし、保存済みの修正を使って未完了のファイルから
自動再開します。UTC 00:00以降に **Run workflow → dev** で手動再開することもできます。
修正済みのファイルでAPIを呼び直しません。

保存先は `sumire-repair-state-v1-*` Artifactで、保持期間は最大14日（リポジトリの保持設定内）です。
復元元は同じリポジトリの `dev` で動いた
[`prepare-upstream-sync.yml`](../.github/workflows/prepare-upstream-sync.yml) の定期・手動実行に限定します。
この準備専用ワークフローでは更新候補のGradleやテストを実行しません。
更新候補を実行する検証・公開は別のワークフローに分離しているため、検証側が同名のArtifactを
作っても途中保存として採用しません。分離前の旧ワークフローのArtifactも復元対象外です。
引き継ぐ更新情報は準備実行のID・再実行番号・リポジトリを照合し、SHA・PR番号も検証します。
追加の署名Secretは不要です。
削除・失効したArtifact、最後のアップロード前の作業は復元できません。
また、ほかのAPIクライアントによる組織共通枠の使用は追跡しないため、組織全体の無料枠や請求額の保証ではありません。
APIキーは定期・手動の修復ステップだけに渡し、Artifactには保存しません。

[OpenAIの無料枠の説明](https://help.openai.com/en/articles/10306912-sharing-feedback-evaluation-and-fine-tuning-data-and-api-inputs-and-outputs-with-openai)
に従い、対象組織・プロジェクトのデータ共有を有効にし、無料枠の登録表示と正の残高を確認してください。
Launch/Growの対象モデル群は合計1M/日、Buildは250K/日で、入力と出力を合算し、UTC 00:00にリセットされます。
日次上限を超えるリクエストは、そのリクエスト全体が通常料金になります。
コードの競合と周辺情報が共有対象のAPIに送られるため、共有可能なプロジェクト専用のキーを使用してください。
Codexはローカルの読み取りツールを使います。無料枠の公式説明ではツール利用は対象外とされているため、
Codexの利用全体が無料になることは保証しません。
APIキーは信頼済みの予算ゲートウェイだけが使い、Codexや検証・マージ・署名ジョブには渡しません。

### 上流履歴が分岐した場合

取り込み済みの上流コミットが、新しいリリースとSumireの両方の祖先であることを確認します。
分岐していればAPIを呼ばず停止します。コミットの組み合わせによる自動的な例外は設けません。
今回の `v1.7.135` と `v1.7.150` は履歴が分岐しているため、引き続き自動処理を止めます。
テストコードの競合自体は、履歴が正常であれば自動修復の対象です。
上流の変更とフォークの差分を人が確認し、通常の作業ブランチで取り込み・検証した後に
`.github/upstream.json` を更新してから、定期同期を再開します。

## 自動マージの条件

準備完了を受けた **Validate and publish upstream update** で以下を実行し、
すべて成功した場合のみ検証済みSHAをマージします。
`GITHUB_TOKEN` が作成したPRに別のPRワークフローが起動することには依存しません。

1. 更新スクリプトの単体・ローカルGit統合テスト
2. フォークのアプリID、signature権限、Provider、通知呼び出しの保持チェック
3. `:app:assembleLiteStandardDebug`
4. `:app:testLiteStandardDebugUnitTest`（Sync bridgeの既存テストを含む）
5. `:app:lintLiteStandardDebug`

Full版のモデル取得・ネイティブビルド、実機/エミュレータでの入力・IPC動作はこの条件には含まれません。
検証用ジョブには書き込みトークンや署名Secretを渡しません。
マージ直前にPRのSHAと `dev` のSHAを再確認します。ブランチ保護や必須レビューを迂回しません。

## APKの自動公開

`Validate and publish upstream update` が `Android Release CI` を再利用ワークフローとして直接呼び出します。
`GITHUB_TOKEN` によるタグ作成だけでは別ワークフローが起動しないため、タグpushイベントには依存しません。
手動の場合は **Android Release CI → Run workflow → ref: dev** で実行できます。
公開対象は `dev` に取り込み済みのコミットに限定し、公開直前にも同一SHAでLiteビルド・全単体テスト・Lintを実行します。

- Full Standard: arm64-v8a / x86_64
- Lite Standard: arm64-v8a / x86_64
- Lite F-Droid: universal
- `SHA256SUMS`: 上記5つのAPKのハッシュ

5つのAPKをすべてビルドし、署名検証、以前の公開済みFull arm64 APKとの証明書一致、
アプリID、バージョン名・コードを確認します。versionCodeが以前より増えていなければ停止します。
署名ビルドのみに既存Secretを渡し、Gradle configuration cacheには保存しません。
署名付きビルドと公開は別ジョブとし、書き込みトークンは公開ジョブだけに渡します。

ビルド成功後にタグを作成し、ドラフトに6ファイルをアップロード、GitHub上のハッシュを照合してから公開します。
公開済みの同じバージョンはスキップし、タグの移動や公開済みAPKの置き換えは行いません。
中断したドラフトは同じタグのコミットから再ビルドして復旧します。
初回の署名比較用に、既存の正常な公開リリースが必要です。

## フォーク独自の手動リリース

上流の正式リリースを待たずに、`dev` に統合した変更を公開する場合の手順です。
ビルド専用ブランチは不要です。通常の機能統合や `dev` へのpushだけでは公開されません。

1. 公開する変更を検証して `dev` に統合します。
2. リリース準備用PRで `app/build.gradle` の `versionName` を、取り込み済みの上流番号に
   正の整数を1つ追加した番号（例: `1.7.128.2`）へ変更します。
   `versionCode` も過去に配布したAPK（一時ビルドを含む）から増やします。
   `.github/upstream.json` は上流の記録なので変更しません。
3. 検証・統合後、そのコミットに対応するタグ（例: `v1.7.128.2`）を作成してpushするか、
   **Android Release CI → Run workflow → ref: 対象コミットSHA** を実行します。
   どちらも検証後に署名付きAPKをGitHub Releasesへ公開する操作です。

タグ・アプリバージョンの一致と、上流番号の一致（例: 上流 `v1.7.128` に対して `1.7.128.2`）を確認します。
公開対象のコミットは `origin/dev` に統合済みである必要があります。
既存タグは動かさず、公開済みAPKも上書きしません。再実行は既存タグのコミットを使います。
新しい上流（例: `v1.7.129`）への自動追随と公開は、従来どおり継続します。

リリースをまだ行わない場合は、バージョン変更・タグpush・Android Release CIの手動実行をせず、
追加修正を通常のPRで `dev` に統合してください。

## GitHub側の設定

- Actionsを有効にしてください（フォークでは無効になっている場合があります）。
- Settings → Actions → General → Workflow permissions の
  **Allow GitHub Actions to create and approve pull requests** を有効にします。
  デフォルト権限はreadのままで構いません。必要な書き込み権限はジョブごとに指定しています。
- Settings → General の **Allow merge commits** が必要です。
- GitHubの「Allow auto-merge」設定やPATは不要です。検証後のジョブがマージAPIを呼びます。
- 必須レビュー等を設定した場合、その条件が満たされるまでマージAPIは失敗します。
- 署名Secret: `KEYSTORE_BASE64` / `KEYSTORE_PASSWORD` / `KEY_ALIAS` / `KEY_PASSWORD`。
  未設定の場合は対応する `ANDROID_KEYSTORE_*` / `ANDROID_KEY_*` にフォールバックします。
  既存リリースと同じ署名を使ってください。必要なモデルに認証が必要な場合は `HF_TOKEN` も設定します。

## 停止した場合

予算到達による一時中断は翌日の定期実行で自動再開します。手動での再開も可能です。
モデルが大きい・破壊的・判断困難とした変更、APIで解決できない競合、上流履歴の分岐、
自動化コードの変更、連携の欠落、テスト失敗は確認が必要です。
Actionsの失敗ログとアップロードされた `fork-validation-*` のレポートを確認してください。
競合の解決に失敗した場合はPRを作成せず停止します。
Actionsの通知設定で失敗通知を受け取れるようにしてください。

- 一時的なビルド失敗: **Validate and publish upstream update** の失敗した実行を再実行します。
- マージ後の公開失敗: 次回の自動追随で再試行されます。すぐ復旧する場合は
  `Android Release CI` を手動実行します。署名・バージョン不一致なら原因を修正してから再実行してください。
- 公開済みリリースの欠損: 自動上書きをせず停止します。既存のタグとAPKを確認し、手動で復旧してください。
- 検証中に `dev` が進んだ: 新しいワークフローを開始します。旧PRは手動で閉じてください。
- 競合やコード修正が必要: 通常の作業ブランチで上流タグをマージ・修正し、
  `.github/upstream.json` を更新してPRを作成します。手動更新PRにも Fork validation が実行されます。
- 既存の自動更新ブランチを手で変更・PRを閉じた: 自動処理はその状態を上書きしません。
  手動で検証・マージするか、不要なPR/ブランチを整理してから再実行します。

新しい準備を停止するにはActionsで **Sync upstream release → Disable workflow** を選択します。
開始済みの検証・公開も止める場合は、その実行をキャンセルしてください。
